# 定位与边界（MUST）

- 本 skill 由你（主模型）**亲自执行**，不调用任何 subagent；也不是全量更新。全量汇总更新走 `collect-update-memory`（用户主动要求时调用，委托 subagent），与本 skill 互不替代。
- **局部更新**：只依据当前对话和任务过程中确认的事实，更新需要更新的主题文件（可新建）；不扫描全部代码，不读取全部记忆，只读取本次涉及主题的 `MEMORY.md` 索引与相关正文。
- **不创建 git commit**：只修改工作区文件；git 提交说明与提交由 `collect-update-memory` 流程负责。
- **排除范围（MUST）**：
  - 不维护 `.project-memory/TODO/`（STEP.md 长期计划、TODO.md 用户待办）——TODO 状态更新由主模型直接处理，不使用本 skill。
  - 不维护 `.project-script/`（验证脚本的创建、复用、清理与 `MEMORY.md` 索引同步）——实时更新方式见 CLAUDE.md「本地验证脚本」节。
  - 不更新 `.project-memory/Documents/`：用户上传文档的主题，正文默认只读；其记忆索引由 `collect-update-memory` agent 同步维护，不由本 skill 更新。

# 触发时机

- 任务进行中或任务结束都可使用：对话中用户提出需要记下来的关键信息（偏好、约束、设计决定、环境事实、命令等），或执行过程中发现可验证的新事实时。
- 无可沉淀内容时直接结束，不新建空文件、不加空索引项。

# 更新流程（MUST）

1. **定位主题**：判断事实归属 `.project-memory/` 哪个大主题（Commands/Environment/Target/Design/Boundary，归属原则见下文）。Documents 由 `collect-update-memory` agent 维护，不在本 skill 范围。
2. **读取该主题 `MEMORY.md` 索引**：通过索引描述判断内容应归入哪个已有正文文件；需要时才读取该正文。不读取无关主题。
3. **写入正文**：
   - 优先归入已有正文文件（同一对象/同一工作流/同一设计问题），更新或补充对应章节，替换过时内容。
   - 归入已有文件不匹配时，按主题语义新建 `<主题名>.md` 并在同轮把索引行写入该主题 `MEMORY.md`。
   - 索引行格式：`- [文档名称](文档名称.md) - 覆盖范围、关键对象及应当读取该文档的任务场景。`
4. **收尾校验**：本次涉及主题内正文文件与索引行一一对应，无断链、无遗漏索引、无孤儿文档；删除过时描述、避免重复事实。

# 记忆范式与格式规则

`.project-memory/` 采用**索引 + 分块文件**的项目记忆范式组织项目记忆，目的是把每次对话注入的提示词从「全量正文」降到「短索引」，正文按需读取。

## 总体结构

管理以下六个大主题目录（每个含 `MEMORY.md` 纯索引 + 同级若干正文文件；本 skill 只写其中五个，Documents 排除）：

```text
.project-memory/
├── Commands/
├── Environment/
├── Documents/
├── Target/
├── Design/
└── Boundary/
```

每个主题目录必须采用以下结构：

```text
主题目录/
├── MEMORY.md            # 纯索引，由 CLAUDE.md 用 @ 注入每次对话
└── <正文文件>.md         # 每个正文文件有明确独立职责，按主题划分
```

## 铁律（不可动摇）

1. **MEMORY.md 永远只保存索引，绝不承载正文。** MEMORY.md 会被 CLAUDE.md 用 `@` 注入每次对话提示词，一旦承载正文就会随项目推进不断累积，回到「提示词膨胀」的痛点。哪怕某主题正文只有几行，也必须写入同级正文文件，不得写入 MEMORY.md。没有例外，没有「小主题可写进 MEMORY」。
2. **正文文件存在则必须在 MEMORY.md 索引里有对应行，不存在不在索引里的正文文件。** 每个正文文件都有明确独立职责，没有"默认正文文件""兜底文件""杂项文件"——这类无职责的兜底文件会成为什么内容都往里塞的垃圾桶，越填越满最后还需手动拆分。
3. **明确可分的类型就分开建文件，不要用粗粒度兜底文件收纳。** 例如 Commands 主题不要用"基础操作.md"兜底，安装依赖、构建、评估、部署、调试各自独立建文件并各自加入索引。粒度由主题边界决定，不由内容多少决定。
4. **新内容优先归入已有小主题文件，只有形成新的独立主题时才新建文件。** 高度相关、属于同一对象或回答同一主要问题的新内容，必须更新或补充到已有文件，不得新建近似文件。从源头防止碎片化。
5. **主题正文累积过长时再分成小主题拆分**，见「文件拆分与合并触发」条件。

## MEMORY.md 索引格式

标题按主题固定为英文短语，其余统一：

```md
# Index Paths and Summaries Related to <Topic>

- [文档名称](文档名称.md) - 覆盖范围、关键对象及应当读取该文档的任务场景。
```

`<Topic>` 固定映射：Boundary→`Project Boundaries`、Target→`Project Targets`、Design→`Project Design`、Documents→`Project Documents`、Environment→`the Development Environment`、Commands→`Common Commands`。

每条索引必须帮助判断两件事：

1. 文件里是否有相关内容；
2. 当前任务是否值得读取这个文件。

因此每条索引应说明：**覆盖范围 + 关键对象 + 读取条件**；容易混淆时补充**排除范围**；可附稳定关键词或代码路径（如类名、入口文件）。

描述质量标准："让 agent 通过索引描述就能直接判断要找的东西在不在里面，以及该不该读"。

索引描述只用于路由定位，不得复述频繁变化的实现细节（如具体参数值、内部路径），也不得作为完成任务所需事实的替代品。索引越接近"路由契约"，越不容易失效。

## 六个大主题的职责

每个主题下的正文文件按"候选小主题"或项目真实主题划分，每个正文文件有明确独立职责。**不设默认/兜底正文文件**——没有内容时不建文件，有内容时按类型建独立文件并加入索引。

| 大主题      | 职责（只回答什么）                                                                                             |
| ----------- | -------------------------------------------------------------------------------------------------------------- |
| Commands    | 怎样安装、运行、构建、评估、调试项目；命令从哪个目录执行、依赖什么、预期结果、常见失败恢复                     |
| Environment | 项目在什么系统/运行环境工作；软件、框架及关键版本；硬件与计算资源；数据/模型/日志/输出路径；环境变量；平台限制 |
| Documents   | 用户上传的项目相关文档（只读），只由 collect-update-memory agent 更新索引                                                |
| Target      | 项目为什么存在；当前要解决什么问题；最终目标；阶段目标；用何标准判断目标达成                                   |
| Design      | 当前项目已有代码的：系统整体怎样组织；各模块职责；模块如何协作；为何采用当前设计；关键策略/方案设计与理由      |
| Boundary    | 哪些行为必须保持；哪些明确不做；数据/模型/接口/实验的限制；哪些修改被禁止                                      |

**事实归属原则**：同一项目事实只能有一个权威归属位置，其他文档通过相对链接引用，不得复制大段相同说明。实现过程中的新事实必须归入对应主题（Design/Boundary/Environment/Commands），不得持续追加到 Target。

## 候选小主题清单

以下候选小主题是划分参考，项目实际需要哪些由当前代码与任务决定。**只有已有可验证内容并形成独立操作或阅读单元时才创建文件**；不创建空文件、空索引项、"暂无内容"占位项。明确可分的类型就各自独立建文件，不要用粗粒度兜底文件收纳。

- **Commands**：按工作流类型分文件，例："环境安装与依赖、数据准备与转换、构建、测试与评估、部署与导出、调试与故障恢复"等独立主题。**不要用"基础操作""Commands总览"这类兜底文件**把所有命令堆在一起。
- **Environment**：例："软件与依赖版本、硬件与计算资源、路径与存储布局、环境变量与外部依赖、远程与容器环境"等。
- **Target**：例："研究问题与总体目标、阶段目标与里程碑、验收标准"等。
- **Design**：例："模块架构、模块设计、关键策略、方案设计、设计决策"等独立主题。针对已有代码的当前设计，而非未来需求。
- **Boundary**：例："数据与标注边界、模型与接口约束、实验与评价边界、禁止事项与非目标"等独立子主题。

Commands 按用户任务和完整工作流分类，**不按 Python/Git/Docker/Shell 等工具名称机械分类**。

## 职责明确主题规则

不得创建"其他.md""杂项.md""补充说明.md""基础操作.md"等无明确职责的兜底文件。按以下顺序处理：

1. **优先归入已有正文文件**：属于同一对象、同一工作流、同一设计问题或同一读取目的时，更新原有描述、补充现有章节或新增语义明确的子章节，删除或替换过时内容。
2. **不建兜底文件**：找不到合适的已有文件时，不要为了"先存下来"而创建无职责的兜底文件。用语义明确的小主题作为单独的文件，等待后续扩充。
3. **达到独立主题条件后建文件**：某类内容满足以下任一条件时，新建独立文件并加入 MEMORY 索引——已形成完整工作流；已含三个以上相互关联的操作或事实；已有独立读取场景；后续更新通常不影响其他文件；普通任务经常只需读取这类内容。

特殊限制：

- 新的项目约束不得塞入 Target，必须归入 Boundary。
- 新的实现事实不得塞入 Documents 或 Target，必须归入 Design。
- 单条未经验证的命令不得进入任何持久化文档。

## 相似小主题的合并与拆分标准

判断两个小主题是否写入同一文件时，比较以下六个维度，每项一致计一项：

1. 是否回答同一个主要问题；
2. 是否围绕同一个核心对象或机制；
3. 是否具有相同或连续的输入输出语义；
4. 是否具有相同的主要执行阶段和状态变化；
5. 是否具有相同的执行结果或验证逻辑；
6. 是否通常由同一类代码变更触发更新。

| 一致维度数         | 处理方式                                                                                                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 5–6 项（高度相同） | **必须**合并到同一文件，用不同章节区分配置/模式/变体。不因类名、入口名、配置名或执行位置略不同就新建文件                                                                                                                          |
| 3–4 项（中等相似） | **默认**合并到同一文件的不同完整章节。不提取单独的"公共主流程文件"；可设"共同背景/变体 A 完整流程/变体 B 完整流程/关键差异"章节，每个变体章节须能独立说明关键输入、处理位置、输出、验证。允许重复必要的流程骨架以避免强制联合读取 |
| 0–2 项（低度相同） | 视为新的独立主题，新建文件并加入索引                                                                                                                                                                                              |

**中等相似主题的例外拆分条件**（同时满足至少两项才允许拆成两个文件）：两个主题通常由不同任务分别读取；由不同代码区域独立演化；修改其一通常不需检查另一个；拥有不同入口/最终输出/验证方式；合并后文件预计超过约 250–300 行；任一独立章节已超过约 100–150 行；共同内容不足各自正文约 30%；合并后需大量"前述内容不适用于本节"的例外说明。

即使拆分，每个文件也应自包含，**不建立只能通过联合读取才能理解的"公共主流程 + 差异补丁"文件结构**。

## 文件拆分与合并触发

拆分由**语义边界**决定，行数和字符数只作为辅助警报：

- 出现以下情况应考虑拆分：一个文件回答多个相互独立的问题；不同部分有不同读取条件；不同部分由不同代码路径触发更新；普通任务通常只需其中一部分；文件超过约 150–250 行或含多个独立读取条件。
- 出现以下情况应考虑合并：两个文件总是同时读取、同时修改；脱离彼此无法理解；都很短且职责高度关联；为避免重复各含大量"参见另一文件"。
- 典型任务应尽量只需读取 1–3 个语义完整文档，不能仅通过增加文件数量制造表面上的短文件。

## MEMORY 索引同步规则

MEMORY 由你直接维护，不引入自动生成脚本。区分"结构变化"和"内容变化"：

- **结构变化必须在同一次任务内原子同步**：新建、删除、重命名、移动、拆分或合并正文文件时，必须同步更新对应 MEMORY.md。这是结构操作的一部分，不是"收尾时尽量更新"。
- **内容变化只检查、不机械改索引**：修正函数名、更新参数、补充实现细节、修复验证方式等，若文档仍负责同一件事，索引无需变化。读取当前索引条目判断"路由契约"是否仍准确，只有职责/范围/名称/路径/读取条件变化时才修改索引。
- **收尾校验范围与变更范围匹配**：普通内容更新只校验受影响文件及其索引；目录结构变化时核对该主题全部正文文件与 MEMORY。
- **结构更新结束时必须确认**：主题目录中实际存在的正文文件集合 == MEMORY.md 中被索引的正文文件集合（MEMORY.md 自身不索引）。不得存在断链、遗漏索引或孤儿文档。

## 硬性规则

- 必须使用本文规定的标题和字段名，不要自由改格式。
- `.project-memory/` 下的项目记忆文件只写真实项目事实，不写教程、模板说明、生成规则，也不记录修改历史、讨论过程或按时间追加的实现发现。
- 更新项目记忆前必须检查当前代码、配置、脚本和实际变更情况，不得仅依据对话描述、旧文档、类名或注释推测实现；文档与可验证现状冲突时，以当前实现为准修正或删除过时描述。
- 不将计划、建议、候选方案、待确认内容或尚未实现的设计写入事实文档。
- 不在持久化文档中写入密码、令牌、私钥、Cookie 或其他可直接使用的凭证，只记录环境变量名称和配置方式。
- 收尾时必须检查本次涉及范围内的过时描述、重复事实、命名不一致、无效链接、索引遗漏和不必要的内容追加。

## 方案更新需确认

设计类文档（Boundary/Target/Design）的方案变更先与用户确认后再写入；工作方式、命令约定等纯事实偏好可直接记录。

| 场景                                                 | 使用                                         |

| 对话/任务中发现需要记下来的关键信息，实时局部更新    | 本 skill（主模型亲自改，不提交 git）         |
| 用户主动要求的阶段性汇总、全量同步、git 提交说明整理 | `collect-update-memory` skill → `collect-update-memory` subagent |
