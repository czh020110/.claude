# 文档更新规则

## 1. 适用范围

- 适用于项目设计类文档（项目目标、项目设计、项目边界等）的方案更新与修改。
- 适用于对 `update-docs` agent/skill 的调用时机和职责边界的说明。

---

## 2. `update-docs` agent 职责边界

- `update-docs` agent 是**一次性汇总和更新文档**的专用工具，只在用户主动要求时调用。
- 它**不负责在开发过程中随代码变更实时更新项目文档**；开发过程中的代码变更不会自动触发文档更新。
- 每次调用是一次性的完整流程：分析变更 → 检查文档 → 更新文档 → 按需提交。
- 开发过程中如果需要更新文档，由主 agent 自己直接修改，不需要调用 `update-docs`。

---

## 3. 方案更新（设计类文档的直接修改）

当用户提出新的设计思路、方案变更、架构调整、项目边界或打算后续使用的新方向时，主 agent 应**直接修改**相关设计类文档（项目目标、项目设计、项目边界等），不通过 subagent。

### 3.1 触发场景

- 用户明确提出新的设计思路或方案，打算后续使用。
- 用户指出项目文档中已有内容与当前实际情况不一致，需要变更。
- 用户主动要求添加或修改设计方案。
- 用户指出项目中的一个明确的边界时。

### 3.2 必须遵守的流程（MUST）

1. **分析可行性**：主 agent 必须先分析用户提出的方案是否可行，包括：
   - 是否与现有架构冲突
   - 是否与当前阶段目标矛盾
   - 是否存在明显的技术风险或依赖问题
   - 如有必要，先读取相关项目文档（项目目标、项目边界、项目设计）确认上下文

2. **与用户讨论**：主 agent 必须主动向用户提问确认，包括：
   - 简要说明对方案可行性的分析结论
   - 指出潜在风险或冲突（如有）
   - 明确提问："是否确认采用这个方案？"
   - 不得在用户确认前直接修改文档

3. **达成一致后修改**：双方（agent 和用户）达成一致后，主 agent 才能修改相关文档。

4. **修改范围**：
   - 只修改与新方案直接相关的文档和条目
   - 不顺手修改无关内容
   - 修改内容必须标注来源（如"基于用户提出的 XX 方案"）

### 3.3 不可行的处理

- 如果分析后认为方案不可行，必须向用户说明原因和替代建议，不得直接修改文档。
- 如果方案部分可行但有风险，必须明确指出风险点，由用户决定是否继续。

---

## 4. 项目文档中已有内容需要变更

当项目文档中的内容与当前实际情况不一致时（用户主动提出或 agent 在执行任务时发现），同样适用方案更新的流程：

1. 先分析变更的合理性和影响范围。
2. 向用户确认是否需要修改。
3. 达成一致后由主 agent 直接修改。

不调用 `update-docs` agent 处理这类变更。

---

## 5. 文档格式遵守（MUST）

修改 `.claude_introduction/` 下任何文档时，必须遵守该文档的现有格式和模板结构：

- 优先模仿文档中已有的章节标题、字段命名、条目格式和层级结构。
- 如果文档已有内容，新增条目必须和已有条目格式一致（如列表风格、字段顺序、缩进层级）。
- 如果文档是空模板，必须按文档中已有模板样式填充，不要自创格式。
- 不要破坏已有的格式一致性：不要随意增删章节、不要改字段命名、不要把列表改成段落或把段落改成列表。
- 只有用户明确要求调整文档结构时，才允许修改格式模板本身。

---

## 6. 不适用本规则的场景

- 阶段性开发完成后的文档汇总和提交：使用 `update-docs` skill。
- 项目架构设计的初始生成：使用 `design-project` skill。
- 项目背景、环境、命令等事实性文档的初始化或批量更新：使用 `update-docs` skill。
