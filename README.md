# persistent coding memory

**Persistent coding memory across sessions and across clients.**

[简体中文](README_CN.md) | **English**

[![platforms](https://img.shields.io/badge/platforms-Codex%20%7C%20ZCode%20%7C%20Claude%20Code%20%7C%20CodeBuddy%20%7C%20WorkBuddy%20%7C%20OpenCode-blue)](https://github.com/czh020110/.claude)

This is a template repository, not a runnable software project. It installs a unified set of agents, skills, project memory and verification scripts into any development repo with a single command, so every repo gets the same collaboration rules and the same memory-building capability — agents stop forgetting everything when a session ends, and switching clients no longer means reconfiguring from scratch.

One source is maintained here, and the `sync-project-config` global skill generates and distributes it to all six platforms: **Codex / ZCode / Claude Code / CodeBuddy / WorkBuddy / OpenCode**.

---

## Install it as a global skill and use it

`sync-project-config/` at the repo root is the **global skill install source**. It is not a project-level skill that this project loads automatically.

### Step 1: Install `sync-project-config` into the global skill directory

Copy the whole `sync-project-config/` directory into the global skill directory of your client:

| Client | Global skill directory |
| --- | --- |
| Codex / ZCode | `~/.agents/skills/sync-project-config/` |
| Claude Code | `~/.claude/skills/sync-project-config/` |
| CodeBuddy (domestic build) | `~/.codebuddy/skills/sync-project-config/` |
| WorkBuddy international (`workbuddy`) | `~/.workbuddy-ai/skills/` |
| WorkBuddy domestic (`workbuddy-cn`) | `~/.workbuddy/skills/` |
| OpenCode | `~/.agents/skills/sync-project-config/` — read natively, no symlink needed |

The real directory is always installed into the canonical location `~/.agents/skills/sync-project-config/`. Clients that do not read `~/.agents/skills` get a **symlink** from their own skill directory back to that canonical copy, so there is only ever one copy on disk.

Or just copy the sentence below and send it to your agent, letting it install and initialize everything for you:

```text
Install sync-project-config from the current project root into the global skill directory of the current client, then use it to initialize the current project.
```

### Step 2: Run the sync inside your development repo

Go to the root of the **development repo** you want to initialize or update. The agent detects the client and then runs:

```bash
bash sync-project-config/scripts/sync.sh codex
bash sync-project-config/scripts/sync.sh zcode
bash sync-project-config/scripts/sync.sh claude
bash sync-project-config/scripts/sync.sh codebuddy
bash sync-project-config/scripts/sync.sh workbuddy
bash sync-project-config/scripts/sync.sh workbuddy-cn
bash sync-project-config/scripts/sync.sh opencode
```

An invalid argument prints the usage and exits with code 2.

> `codebuddy`, `workbuddy` and `workbuddy-cn` are separate targets: CodeBuddy uses `~/.codebuddy/skills`, `workbuddy` uses `~/.workbuddy-ai/skills` (international build), and `workbuddy-cn` uses `~/.workbuddy/skills` (domestic build). Installing into the wrong one fails silently rather than erroring.
>
> WorkBuddy's Code mode loads skills **only from the global directory**, so both WorkBuddy variants install the global skill plus one variant-specific symlink and generate **no** project-level `agents/` or `skills/`.

### Step 3: Confirm the result

The script prints staged `[1/7]` through `[7/7]` logs and lists every synced or added file. When it finishes, the target repo should contain:

- The platform-specific `agents/` and `skills/` directories
- `AGENTS.md` (plus `CLAUDE.md` on the Claude platform)
- The `.project-memory/` and `.project-script/` templates
- The extra entries appended to `.gitignore`

## What problems it solves

| Problem | How this repo handles it |
| --- | --- |
| Every AI client (Codex / Claude Code / ZCode / CodeBuddy / WorkBuddy / OpenCode) has its own config directory, so the same prompt gets copy-pasted and maintained N times | Maintain a single source (`.codex/agents/` + `.agents/skills/`); every other platform directory is generated by the script |
| Agents lose all context when a session ends, so project background, constraints and pitfalls have to be explained over and over | The `.project-memory/` index plus chunked body files, combined with `read-index-memory` / `update-memory`, forms a closed memory loop |
| Configurations are lost when you switch machines | The config source lives in a remote Git repo; the script self-updates on every launch |
| Nobody remembers to verify after changing code | The `post-verify` skill enforces a final check, and `.project-script/` accumulates reusable verification scripts |
| Project memory needs to sync across devices and repos | `sync-project-memory` syncs through a `docs/<slug>` branch in a standalone Git repo |

## Core design: single source and generated output

```
Single source (handwritten, only one copy)      Generated output (produced by script, do not edit)
──────────────────────────────────────────      ────────────────────────────────────────────────
.codex/agents/*.toml                     ──┐      .zcode/agents/*.md
  └ developer_instructions is the         ├──→    .claude/agents/*.md
    only prompt body                                                                │      .codebuddy/agents/*.md
                                          │      .opencode/agents/*.md
.agents/skills/<name>/SKILL.md           ─┼──→    .claude/skills/<name>/
  └ scripts/ references/                  │      .codebuddy/skills/<name>/
                                          │      .opencode/skills/<name>/
                                          │      .agents/skills/<name>/ (zcode and workbuddy reuse
                                          │      the global copy via symlink)
AGENTS.md                                ─┴──→    CLAUDE.md (derived on the claude platform)
```

Three hard rules:

1. **Only one copy of the source.** Agent bodies live in `developer_instructions` inside `.codex/agents/*.toml`; skill bodies live in `.agents/skills/<name>/SKILL.md`.
2. **Generated directories are not sources.** `.claude/`, `.zcode/`, `.codebuddy/` and `.opencode/` are sync artifacts and are **never synced back**. Edit them and the next sync overwrites your changes.
3. **Only metadata is adapted, never the body.** Generation only adjusts YAML frontmatter, file names (`_` → `-`), tool permissions and platform directories. The prompt body is preserved verbatim.

| Platform arg | Agent output | Skill output | Extra behavior |
| --- | --- | --- | --- |

| `zcode` | `.codex/agents/*.toml` → `.zcode/agents/*.md` | Reuses `.agents/skills/` | Adapts tool names in AGENTS.md; also copies the global skill to `~/.zcode/skills/` |
| `claude` | → `.claude/agents/*.md` | → `.claude/skills/` | Derives a root `CLAUDE.md` from `AGENTS.md` |
| `codebuddy` | → `.codebuddy/agents/*.md` | → `.codebuddy/skills/` | Uses the global MCP configuration workflow |
| `workbuddy` | none (global only) | none (global only) | Installs the global skill and links it into `~/.workbuddy-ai/skills` |
| `workbuddy-cn` | none (global only) | none (global only) | Installs the global skill and links it into `~/.workbuddy/skills` |
| `opencode` | → `.opencode/agents/*.md` | → `.opencode/skills/` | Adapts `AGENTS.md` tools to `todowrite` / `question`; uses the canonical global copy as-is (OpenCode reads `~/.agents/skills/` natively, so no symlink is created) |

### Adaptation rules during generation

**Agents (`.toml` → `.md`)**

- File name: `code_review_custom` → `code-review-custom` (underscores become hyphens)
- Frontmatter gets `name` + `description` (the description is JSON-escaped so non-ASCII and special characters survive)
- Model and tools are injected per platform:
  - Claude: `code_review_custom` → `sonnet`, `docs_research` → `haiku`
  - ZCode: a uniform `model: glm-5.3-flash`
  - CodeBuddy: `tools` / `disallowedTools` injected from a lookup table (for example the review agent is read-only and may not write)
- Body = the content of `developer_instructions` in the TOML, **preserved verbatim**
- OpenCode: no `name:` key is emitted (the file name is the agent name, and unknown frontmatter is ignored); `mode: subagent` is added, and restrictions use `permission` rather than `tools` (for example the review agent gets `edit: deny`)

**Skills**

- Copies `SKILL.md` + `scripts/` + `references/`
- Excludes `**/agents/*.yaml` (Codex UI only)
- Claude / CodeBuddy: adds `user-invocable: true` when the frontmatter lacks it
- On Claude / CodeBuddy, `sync-project-memory/scripts/sync-memory.sh` has its internal path `.agents/.cache` rewritten to `.claude/.cache` / `.codebuddy/.cache`

**AGENTS.md / CLAUDE.md**

- The upstream `AGENTS.md` wins, but **everything below the `<!-- sync-project-config:custom-prompts -->` marker in the target project is preserved** (everything above the marker is replaced)
- Tool names in the synchronized controlled section are rewritten per platform:

  | Source name | Claude Code | ZCode | CodeBuddy / WorkBuddy | OpenCode |
  | --- | --- | --- | --- | --- |
  | `update_plan` | `TodoWrite` | `TodoWrite` | `TodoWrite` | `todowrite` |
  | `request_user_input` | `AskUserQuestion` | `AskUserQuestion` | `AskUserQuestion` | `question` |

  Claude Code's `TaskCreate`/`TaskUpdate`/`TaskList`/`TaskGet` tools are a separate task system; this prompt uses `TodoWrite`. ZCode may additionally expose the read-only `TodoRead`, and WorkBuddy's implementation class is `TodoWriteTool`, while the prompt-facing name is `TodoWrite`. OpenCode uses the lowercase built-ins `todowrite` and `question` (with `todoread` available as its read-only todo counterpart).

- If that marker is absent from `AGENTS.md`, the whole file is overwritten

## sync.sh execution flow

Every launch **self-updates first**: clone the remote template repo → overwrite `sync-project-config/` in the current project root → `exec` the freshly updated script → then run the remaining steps. So even a stale global install upgrades itself before executing the latest logic.

| Stage | Action | Overwrite policy |
| --- | --- | --- |
| bootstrap | Clone the remote source and overwrite the local `sync-project-config/` | Full overwrite |
| global skill | Install/refresh the global skill directory | Delete then copy |
| `[1/7]` | Use the already-updated remote config source | — |
| `[2/7]` | Sync `AGENTS.md` (+ `CLAUDE.md`) and the global skill | Replace above the marker, keep below |
| `[3/7]` | Generate platform agents and skills | Full regeneration |
| `[4/7]` | Sync `.project-memory/` templates | **Only add missing files, never overwrite** |
| `[5/7]` | Sync `.project-script/` templates | **Only add missing files, never overwrite** |
| `[6/7]` | Check and complete `.gitignore` | Append missing entries only |
| `[7/7]` | Done | — |

Three copy semantics decide what gets overwritten and what does not:

| Function | Semantics | Exclusions |
| --- | --- | --- |
| `copy_tree` | Overwrite whenever the target differs from the source | `.cache/*`, `settings.local.json`, `*.local.json`, `*.secret*`, `*.key`, `.DS_Store`, `CODEBUDDY.local.md` |
| `copy_missing_tree` | Skip if the target already exists | `.DS_Store` |
| `copy_skill_tree` | Overwrite, but adapt `SKILL.md` and the memory sync script per platform | `**/agents/*.yaml`, `.DS_Store` |

> **Key takeaway**: your project memory bodies (`.project-memory/`) and verification scripts (`.project-script/`) are **never overwritten by a sync** — only missing template files are added. You can safely accumulate them in the target project over the long term.

## Built-in skills

Sources live in `.agents/skills/`.

| Skill | Purpose | Trigger |
| --- | --- | --- |
| `sync-project-config` | **Global distribution entry**: initialize/update a project's agents, skills and templates | When the user asks to sync base project config, or config is found missing |
| `read-index-memory` | Read the `.project-memory/` topic indexes and route to bodies as needed | **At the start of every new task** |
| `update-memory` | Write verified, already-implemented local facts into the matching topic | When this round confirmed a valid fact/constraint/preference/lesson |
| `collect-update-memory` | Orchestrates a full memory sync (delegates to `collect_update_memory`) | When the user explicitly asks for a staged or full sync |
| `sync-project-memory` | Push/pull `.project-memory/` to and from the remote memory repo | When the user asks to push / pull / check sync status |
| `post-verify` | Final verification gate for modification tasks; manages scripts and index | **Mandatory before shipping any modification task** |
| `git-commit` | Group changes by convention, generate a structured commit message and commit | When the user explicitly asks to commit/save changes |
| `code-review-custom` | Determine the review scope and delegate to the review agent | When the user explicitly gives a review scope |
| `docs-research` | Organize batched documentation questions and delegate to the research agent | When 3+ external interfaces or a complex version migration must be verified |

### A typical task flow

```
New task starts
  └─ read-index-memory          read indexes, read bodies as needed
       ↓
  (Implement changes: code / config / docs)
       ↓
   post-verify                  verify, fix loop, accumulate scripts into .project-script/
       ↓
   update-memory                write this round's confirmed facts into .project-memory/
       ↓
  (When asked) git-commit → collect-update-memory → sync-project-memory
```

## Project memory system

### Structure: index plus chunked bodies

```
.project-memory/
├── Commands/MEMORY.md      ← index lines only, no bodies
├── Commands/<topic>.md     ← fact bodies
├── Environment/
├── Documents/
├── Target/
├── Design/
├── Boundary/
├── Tools/
├── Pitfalls/
└── TODO/{STEP.md, TODO.md, Pending.md}
```

| Topic | What it records |
| --- | --- |
| `Commands` | Install, run, build, test, evaluate, deploy and recover workflows |
| `Environment` | Tools/versions, hardware, paths, env vars, external services, platform limits |
| `Documents` | User-maintained project docs (bodies are read-only by default) |
| `Target` | Currently effective project purpose, scope and acceptance criteria |
| `Design` | Current architecture, module responsibilities, collaboration model and design rationale |
| `Boundary` | Behavior that must be preserved, out-of-scope items, limits and quality floor |
| `Tools` | Reusable helper scripts, visualizations, statistics or data conversion tools |
| `Pitfalls` | Reusable lessons: applicable scenarios, detection signals, root cause, avoidance |

Rules: one fact keeps exactly one authoritative home; a body file must have an index entry and an index entry must not point at a missing file; any structural change (create/delete/rename/split/merge) must land in the same round as its index.

### The three TODO files

| File | Maintained by | Contents |
| --- | --- | --- |
| `TODO/TODO.md` | **The user** | Ordinary todos; the model may write only when the user explicitly asks |
| `TODO/Pending.md` | The model | Not-yet-implemented plans/designs/decisions, each with background, decision pending, completion criteria and scope |
| `TODO/STEP.md` | The model | Long-term stage breakdown (not used for one-off tasks) |

Checkbox format is uniform: `[ ]` not started, `[-]` in progress, `[x]` done.

**Key separation**: unimplemented plans in `Pending.md` are **not facts** and must never be written into any memory body. Once a plan is implemented and verified, remove its Pending entry and write the real final state into the matching topic. If a plan is rejected, only remove the entry.

## Remote memory sync

`sync-project-memory` treats `.project-memory/` as a **standalone Git repository** and syncs it to a remote, so memory survives across devices.

Entry point (the path varies by platform; use the skill directory actually generated):

```bash
# Codex / ZCode
bash .agents/skills/sync-project-memory/scripts/sync-memory.sh <subcommand>

# Claude
bash .claude/skills/sync-project-memory/scripts/sync-memory.sh <subcommand>

# CodeBuddy
bash .codebuddy/skills/sync-project-memory/scripts/sync-memory.sh <subcommand>

# OpenCode
bash .opencode/skills/sync-project-memory/scripts/sync-memory.sh <subcommand>
```

| Subcommand | Purpose |
| --- | --- |
| `pull` | Fetch and merge remote memory into the local copy |
| `push` | Push local memory to the remote |
| `info` | Show status (no reachability pre-check, always exits 0) |
| `status` | Show detailed status |
| `config <URL>` | Configure the remote memory repo address |
| `diagnose` | Print a summary only, no network pre-check |

**Project identity**: the URL from `git remote get-url origin` in the main code repo maps uniquely to a `docs/<slug>` branch name. The same code repo always maps to the same branch in the remote memory repo, so switching devices needs no extra setup. If the main repo has no `origin`, the script errors out instead of falling back to a local directory name.

**The memory repo address** is stored in `.agents/.cache/docs-sync.conf` (a single plain-text line, **not tracked by Git**), so each device needs its own one-time setup:

```bash
... sync-memory.sh config https://github.com/<you>/<your-project-docs>.git
```

On first use, if `.project-memory/` already has files but is not yet a Git repo, the script brings it under version control and merges automatically. Before pushing it runs a reachability pre-check. A merge conflict aborts the run and leaves conflict markers in the files; resolve them and `push` again, or run `cd .project-memory && git merge --abort` to give up.

## Verification script directory

`.project-script/` holds **reusable verification scripts**, managed by the `post-verify` skill:

- Scripts go under `.project-script/<verification-type>/` by type; do not pile them at the root
- `.project-script/MEMORY.md` records only path, purpose, applicable scenarios, entry command and prerequisites — **never a copy of the script body**
- Adding, deleting, moving or renaming a script must update the index in the same round
- Scripts may read credentials only from environment variables or other secure config; never store API keys, tokens or cookies

Every modification task (including config, template, doc and prompt syncs) must run `post-verify` before delivery. Pure consultation, review and research do not need it.

## Boundaries and safety

What the script **will not** do:

- It does not replace the target project's custom section below the marker; the controlled portion of the root `AGENTS.md` is refreshed from the upstream source and adapts the tool names for Claude Code, ZCode, CodeBuddy, WorkBuddy, and OpenCode. The derived `CLAUDE.md` receives the same Claude mapping.
- It does not treat generated directories as sources, and never syncs back from `.claude/`, `.zcode/`, `.codebuddy/` or `.opencode/`
- It does not overwrite existing `.project-memory/` or `.project-script/` content in the target project
- It does not copy credentials, local caches, `settings.local.json`, `CODEBUDDY.local.md`, or the Codex-UI-only `agents/openai.yaml`
- It is never invoked unless the user explicitly asks for a sync

What memory writes **will not** do:

- Never write passwords, tokens, private keys or cookies
- Never write unimplemented plans, pending decisions, candidate options or change logs
- Never record one-off tool errors, transient environment failures or raw debug logs

## Maintainer guide

### Adding a skill

1. Write the body in `.agents/skills/<name>/SKILL.md`; the frontmatter needs at least `name` and `description`
2. Put scripts in `scripts/` and longer reference docs in `references/`
3. Only add `agents/openai.yaml` for Codex UI display needs (it is not distributed to other platforms)
4. Re-run `sync.sh <platform>` in the target repo to distribute it

### Adding an agent

1. Create `.codex/agents/<name>.toml` with the body inside `developer_instructions = """..."""`
2. It must contain `name` and `description`, otherwise the generator errors out
3. To assign a model or tool permissions for Claude / CodeBuddy, add a row to the `claude_models` / `codebuddy_tools` lookup tables in `sync.sh`; for OpenCode, add a row to `opencode_permissions` (OpenCode restricts via `permission`, not `tools`)
4. Re-run `sync.sh` to generate the per-platform output

### Editing prompts

**Edit only the source, never the generated directories.** After changing `.codex/agents/*.toml` or `.agents/skills/*/SKILL.md`, commit and push to the template repo; the next `sync.sh` run in each development repo pulls the latest version automatically (the script self-updates on launch).

### Editing `AGENTS.md`

Everything **above** the `<!-- sync-project-config:custom-prompts -->` marker is managed (replaced by the remote version); everything **below** it is each project's custom area (preserved). Put common rules above the marker.

## FAQ

**Q: Will a sync wipe the memory I have accumulated in my project?**

No. `.project-memory/` and `.project-script/` use an "add missing only" policy and skip any file that already exists. Only the agent/skill generated directories and the part of `AGENTS.md` above the marker are overwritten.

**Q: Why does the script need network access to clone the repo on first run?**

That is the self-update mechanism: it overwrites `sync-project-config/` in the project root with the latest remote version, then `exec`s the new script. The benefit is that a stale global install immediately gets the latest logic; the cost is that it cannot run offline. For offline use you need a local checkout of the template repo and must set both internal variables to skip the clone:

```bash
SYNC_PROJECT_CONFIG_BOOTSTRAPPED=1 \
SYNC_PROJECT_CONFIG_REMOTE_DIR=/path/to/local/template-checkout \
  bash sync-project-config/scripts/sync.sh codex
```

**Q: I want to use my own fork of the template repo. How?**

Set `PROJECT_CONFIG_REPO_URL` (or the per-platform `CODEX_CONFIG_REPO_URL` / `CODEBUDDY_CONFIG_REPO_URL`) to your repo address.

**Q: Should I use `codebuddy`, `workbuddy` or `workbuddy-cn`?**

Use `codebuddy` for the domestic CodeBuddy build, `workbuddy` for the international WorkBuddy build, and `workbuddy-cn` for the domestic WorkBuddy build. Quick check: `~/.workbuddy-ai/` means `workbuddy`, `~/.workbuddy/` means `workbuddy-cn`, and `~/.codebuddy/` means `codebuddy`. They write to different directories, and the wrong choice fails silently rather than erroring.

**Q: Will WorkBuddy pick up skills placed in the project?**

No. WorkBuddy's Code mode loads skills only from its global skill directory, so both `workbuddy` and `workbuddy-cn` generate no project-level `agents/` or `skills/`. The global `sync-project-config` is installed once as a real directory under `~/.agents/skills/` and linked into the selected WorkBuddy directory. The nine project skills are therefore unavailable under WorkBuddy by design — only the distribution entry point is.

**Q: My client's global skill directory is not the default. What now?**

Override the matching variable — `CODEBUDDY_GLOBAL_SKILL_DIR`, `WORKBUDDY_GLOBAL_SKILL_DIR`, or `WORKBUDDY_SKILL_LINK_DIRS` (colon-separated). These are link targets; the real copy always stays in `CODEX_GLOBAL_SKILL_DIR`.

**Q: `sync-memory.sh` says `Remote memory repository URL is not configured`?**

Create an empty repo on GitHub/GitLab dedicated to project memory (**not** your main project repo), then run `sync-memory.sh config <URL>`.

**Q: After switching devices, do I need to reconfigure memory sync?**

Agents and skills come along with the platform config, so nothing to do there; the project identity comes from the main repo's `origin` remote, so nothing to do there either. Only the remote memory repo URL lives in a local cache and needs `config` run once again.

**Q: Why does OpenCode need no symlink?**

OpenCode searches `~/.agents/skills/<name>/SKILL.md` natively in addition to `~/.config/opencode/skills/` and the Claude-compatible `~/.claude/skills/`. The canonical copy already sits in `~/.agents/skills/`, so it is picked up as-is. Nothing is linked into `~/.config/opencode/skills/` on purpose: OpenCode requires skill names to be unique across all locations, and a second copy pointing at the same name can collide. The project-level copies go to `.opencode/skills/`.

**Q: Where is the MCP configuration?**

The sync script does not generate or copy project-level MCP configuration files. The `sync-project-config` Skill tells the agent to reuse the current client's global `context7` configuration or add it globally when missing.
